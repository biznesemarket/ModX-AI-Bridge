# Работа с ModX AI Bridge: публикация статей и demo-промпты

Практическое руководство для контент-менеджера и владельца сайта. Версия: Stable `0.11.0`
(2026-09-14). Предполагается, что установка и подключение агента уже выполнены
(`docs/guides/installation-and-ai-agent-setup.md`).

Здесь описано, как поручить AI-агенту подготовку статей, обновление материалов, SEO, работу с
шаблонами и TV, а также приведена большая библиотека готовых промптов, которые можно копировать
как есть.

---

## 1. Как пользоваться этой инструкцией

1. Прочитайте разделы 2–3, чтобы понимать слова и границы возможностей.
2. Пройдите раздел 4 («Публикация статьи») один раз вместе с агентом — это базовый сценарий.
3. Дальше пользуйтесь библиотекой промптов (раздел 8): копируйте нужный промпт в чат с агентом и
   меняйте только текст в квадратных скобках `[...]`.

Агент сам вызывает нужные инструменты Bridge. Ваша задача — ставить задачу человеческим языком и
проверять результат.

## 2. Короткий словарь

| Термин | Простыми словами |
|---|---|
| **Ресурс** | Страница/статья/запись в MODX. |
| **Черновик** | Ресурс, который ещё не виден на сайте (`published = нет`). |
| **Публикация** | Делает ресурс видимым на сайте. В Bridge защищена подтверждением. |
| **Шаблон (template)** | Макет страницы. У каждого ресурса есть id шаблона. |
| **TV** | Дополнительное поле страницы (автор, обложка, цена и т.п.). |
| **Content Contract** | Правила: какие поля обязательны и какие у них ограничения. |
| **Content QA** | Автопроверка текста: есть ли H1, нет ли `<script>`, не превышена ли длина и т.п. |
| **Job (задание)** | Запись об асинхронной операции (актуально для REST и Manager-консоли). |
| **Idempotency-Key** | Уникальный «номер операции», чтобы случайный повтор не создал дубль. |
| **Approval (подтверждение)** | Согласие человека на опасное действие (публикация, удаление). |
| **Scope** | Права токена (что агенту вообще разрешено). |

## 3. Что агент умеет и чего не умеет

| Действие | Инструмент | Нужен scope | Подтверждение |
|---|---|---|---|
| Смотрит структуру сайта | `site_schema` | `site:read` | нет |
| Отпечаток структуры | `site_fingerprint` | `site:read` | нет |
| Правила контента для шаблона | `content_contract` | `site:read` | нет |
| Проверяет контент | `content_validate` | `content:validate` | нет |
| Читает один ресурс | `resource_read` | `resource:read` | нет |
| Ищет и перечисляет ресурсы | `resource_list` | `resource:read` | нет |
| Делает предпросмотр | `resource_preview` | `resource:preview` | нет |
| Создаёт черновик | `resource_create` | `resource:write` | нет |
| Обновляет ресурс | `resource_update` | `resource:write` | нет |
| Публикует | `resource_publish` | `resource:publish` | да (по умолчанию) |
| Удаляет | `resource_delete` | `resource:delete` | нет — только политика |

Ключевые ограничения (это защита, а не ошибка):

- **Агент не может опубликовать статью сам по умолчанию** — публикация требует подтверждения
  человеком (`aibridge_approval_required_for_publish = Yes`).
- **Агент не может удалить ресурс по умолчанию** — удаление выключено глобально
  (`aibridge_allow_resource_delete = No`).
- **Осторожно с удалением:** если администратор включит `aibridge_allow_resource_delete` и выдаст
  scope `resource:delete`, удаление через MCP/REST выполняется **без отдельного подтверждения** —
  удаление защищено только политикой. Approval для удаления возникает только в менеджерском
  workflow (кнопка «Delete Job» в консоли), а не в прямом API-вызове. Поэтому scope `resource:delete`
  выдавайте лишь тогда, когда осознанно доверяете агенту удаление.
- **Агент не может менять системные настройки** — нет scope и операция заблокирована.
- **Публикация и удаление не проходят «мимо» проверок**: сначала безопасность, затем Content QA,
  снимок состояния, транзакция, инвалидация кэша и запись в аудит.
- **Черновики безопасны**: пока ресурс не опубликован, он не виден посетителям.

## 4. Главный сценарий: подготовка и публикация статьи

Ниже — сценарий «статья на сайт». Вы общаетесь с агентом обычным текстом; агент сам вызывает
инструменты. Значения `[в квадратных скобках]` замените на свои.

### Шаг A. Узнайте шаблон и правила

Промпт:

```text
Посмотри структуру сайта через Bridge и покажи таблицу:
id шаблона, название, сколько ресурсов использует этот шаблон.
Отдельно перечисли TV (дополнительные поля), которые относятся к каждому шаблону.
```

Затем:

```text
Сформируй Content Contract для шаблона [ID]. Объясни простыми словами:
какие поля обязательны, какие ограничения по длине и какие SEO-рекомендации.
```

### Шаг B. Подготовьте текст

Промпт:

```text
Напиши статью на тему «[ТЕМА]» для шаблона [ID].
Требования: один H1, заголовок до 60 символов, meta description 120–160 символов,
2–4 подзаголовка H2, объём около [800] слов, дружелюбный деловой тон, без воды.
Выведи текст, пока не создавай ресурс.
```

### Шаг C. Проверьте текст до сохранения

Промпт:

```text
Проверь подготовленную статью по Content Contract шаблона [ID] с помощью content_validate.
Покажи ошибки и предупреждения списком. Если есть ошибки — исправь текст и проверь снова.
```

### Шаг D. Создайте черновик

Промпт:

```text
Создай черновик статьи с помощью resource_create:
шаблон [ID], родительская страница [ID родителя или 0 для корня],
pagetitle — «[ЗАГОЛОВОК]», alias — [латиницей-через-дефис],
content — подготовленный HTML, tvs — [перечислите, если нужны].
Сгенерируй новый уникальный idempotency_key. Не публикуй статью.
Сообщи: id созданного ресурса, прошла ли Content QA, есть ли предупреждения.
```

Что важно: агент должен создать **черновик**. Он не сможет случайно опубликовать статью, даже если
попросит, пока публикация не подтверждена.

### Шаг E. Просмотрите и доработайте

Промпт:

```text
Покажи ресурс [ID]: заголовок, alias, шаблон, родителя, признак публикации, все TV и текст.
```

```text
Обнови ресурс [ID] через resource_update: замени вступление на «[...]»,
добавь подзаголовок «[...]», сократи текст до [600] слов.
Новый idempotency_key, повторную публикацию не выполняй.
```

Лучше править по одному смысловому изменению за вызов — так проще откатить.

### Шаг F. Предпросмотр перед публикацией

Промпт:

```text
Сделай безопасный предпросмотр ресурса [ID] с новым текстом (resource_preview).
Ничего не сохраняй. Покажи, как будет выглядеть страница, и предупреди о проблемах.
```

### Шаг G. Публикация

Способ 1 — **самый простой и безопасный для владельца сайта** (рекомендуется):

1. Агент готовит и проверяет черновик (шаги A–F).
2. Вы открываете этот черновик в обычном редакторе MODX Manager и нажимаете «Опубликовать».

Это стандартное действие MODX, оно не требует подтверждений Bridge и полностью в ваших руках.
Учтите: такая публикация идёт «нативно» через MODX и не фиксируется в аудите Bridge как операция
`resource.publish` — это нормально для ручного редактирования человеком.

Способ 2 — **публикация агентом после подтверждения** (для продвинутых/автоматизации):

1. Администратор подтверждает изменение (approval) — это делается серверным workflow Bridge и
   привязывается к конкретному изменению и конкретному ресурсу.
2. После подтверждения агент получает `approval_id` и `change_id` и публикует:

```text
Опубликуй ресурс [ID] через resource_publish, используя
approval_id=[...] и change_id=[...]. Новый idempotency_key.
Сообщи результат и статус.
```

Что произойдёт без подтверждения: агент получит ответ `approval_required` или `approval_invalid`.
Это нормальная защита. В версии `0.11.0` в Manager-консоли нет кнопок подтверждения — их
выполняет администратор через серверный workflow.

Способ 3 — **полностью автоматическая публикация** (не рекомендуется):

Если администратор выключит `aibridge_approval_required_for_publish`, агент сможет публиковать без
подтверждения — ему достаточно scope `resource:publish` и idempotency_key. Это удобно для
полностью автоматических конвейеров, но снимает «человеческий предохранитель». Включайте только
осознанно.

## 5. Другие функции Bridge

### 5.1. Чтение и поиск

- `resource_read` — один ресурс по id со всеми TV.
- `resource_list` — список с фильтрами: `parent` (+ `depth` 1..50 для потомков), `template`,
  `context_key`, `published`, `tv_name`/`tv_value`, `q` (поиск по заголовку/alias/описанию),
  `limit` (1..100, default 25), `offset`, `sort`, `dir`.
- В списке возвращается облегчённая карточка (без полного текста и TV) плюс `count`, `total`,
  `limit`, `offset`.

### 5.2. Структура сайта

- `site_schema` — шаблоны, TV и ресурсы (можно ограничить `limit`, `root_id`, `context_key`,
  `template_id`).
- `site_fingerprint` — «отпечаток» структуры; удобно, чтобы понять, менялась ли конфигурация.
- `content_contract` — правила контента для шаблона.

### 5.3. Контроль качества

- `content_validate` — проверяет предложенный контент по контракту и возвращает `errors` и
  `warnings`. Ошибки блокируют сохранение, предупреждения — нет, но их полезно исправлять.

Типичные ошибки QA: нет H1 или их несколько; поля короче/длиннее допустимого; есть `<script>` или
`<iframe>`; сломан JSON-LD. Типичные предупреждения: слишком короткий/длинный SEO-заголовок,
отсутствует JSON-LD, пустые ссылки.

### 5.4. Работа с TV

Агент читает TV в карточке ресурса (ключ — имя TV) и пишет их через объект `tvs` при create/update:

```json
{ "tvs": { "author": "Иван Петров", "reading_time": "7", "cover": "images/cover.jpg" } }
```

Структурированные значения (например, MIGX/JSON) храните как строку JSON.

Если в TV хранится что-то секретное (ключи, пароли, персональные данные), попросите администратора
добавить имя этого TV в настройку `aibridge_redacted_tvs` (JSON-массив имён). Тогда агент вообще не
увидит значение этого TV при чтении ресурса — ключ не попадёт в ответ.

### 5.5. Задания (jobs) — только для REST/Manager

Изменения через REST и Manager-консоль выполняются асинхронно. Статус: `GET /api/ai/v2/jobs/{id}`
(поля `status`, `progress`). MCP-агент выполняет запись синхронно и статус ему не нужен.

## 6. Системный промпт для агента (вставьте один раз)

Скопируйте этот блок в настройки/инструкции вашего AI-ассистента. Он задаёт правила безопасной
работы с Bridge.

```text
Ты — контент-ассистент сайта на MODX, работающий через ModX AI Bridge (MCP).

Правила:
1. Перед созданием статьи всегда: вызови site_schema, чтобы узнать шаблоны;
   вызови content_contract для нужного шаблона; проверь черновик content_validate.
2. Создавай новые материалы только как черновики (resource_create) и никогда не подразумевай,
   что они опубликованы.
3. Для каждого изменяющего вызова генерируй новый уникальный idempotency_key (8–190 символов).
   Не переиспользуй ключ для другого изменения.
4. Не публикуй и не удаляй ресурсы без явного approval_id и change_id от человека.
5. Если операция отклонена (approval_required, policy_denied, operation_disabled) — объясни
   причину простыми словами и предложи, что может сделать администратор. Не пытайся обходить защиту.
6. Никогда не спрашивай и не сохраняй токен Bridge в переписке. Не выводи секреты.
7. Перед перезаписью существующего текста сначала покажи, что именно изменишь.
8. Отвечай на русском, коротко и по делу. В конце каждой записи сообщай: id ресурса, статус
   публикации, прошла ли QA, какие предупреждения остались.
```

## 7. Библиотека demo-промптов

Копируйте промпт целиком. Заменяйте только `[значения]`.

### 7.1. Разведка сайта и планирование

1. ```text
   Покажи структуру сайта: контексты, шаблоны, привязанные TV и количество ресурсов по шаблонам.
   Оформи как таблицу.
   ```

2. ```text
   Какие шаблоны существуют на сайте? Для каждого укажи id, название и назначение,
   которое можно предположить по имени и по типу ресурсов.
   ```

3. ```text
   Сформируй Content Contract для шаблона [ID] и объясни простыми словами, что обязательно,
   а что рекомендация.
   ```

4. ```text
   Покажи дерево страниц от корня (depth [2]) — только id, заголовок и родитель.
   ```

5. ```text
   Найди все страницы в контексте [web], у которых заполнено TV [tv_name]. Покажи id,
   заголовок и значение этого TV.
   ```

6. ```text
   Сравни структуру сайта с прошлым отпечатком. Что изменилось: шаблоны, TV, ресурсы?
   ```

7. ```text
   Предложи контент-план из [10] тем для раздела «[ТЕМА РАЗДЕЛА]». Для каждой темы:
   рабочий заголовок, целевая аудитория, ключевые вопросы читателя. Ресурсы пока не создавай.
   ```

### 7.2. Создание статей

8. ```text
   Напиши статью «[ТЕМА]» для шаблона [ID] объёмом около [900] слов: один H1, подзаголовки H2,
   короткие абзацы, примеры. Выведи текст без создания ресурса.
   ```

9. ```text
   Создай черновик статьи «[ЗАГОЛОВОК]» для шаблона [ID], родитель [ID родителя],
   alias [alias-латиницей], контент — как выше. Не публикуй. Сообщи id ресурса.
   ```

10. ```text
    Создай черновик новости на тему «[СОБЫТИЕ]» для шаблона [ID]: объём [300] слов,
    один H1, дата [2026-09-20] в поле [поле/TV]. Не публикуй.
    ```

11. ```text
    Создай черновик страницы услуги «[УСЛУГА]»: структура — что это, кому подходит,
    как проходит, цена, частые вопросы. Шаблон [ID], не публикуй.
    ```

12. ```text
    Создай черновик лендинга «[НАЗВАНИЕ]»: hero-блок, 3 преимущества, отзыв,
    призыв к действию. Шаблон [ID], не публикуй.
    ```

13. ```text
    Создай черновик статьи-инструкции «Как [действие]»: пошаговый список, скриншоты
    опиши текстом, итоговый чек-лист. Шаблон [ID], не публикуй.
    ```

14. ```text
    Создай черновик статьи «[ТЕМА]» с таблицей сравнения [A] и [B] и списком выводов.
    Шаблон [ID], TV author = «[АВТОР]», не публикуй.
    ```

15. ```text
    Создай сетку из [5] черновиков по темам: [ТЕМА 1], [ТЕМА 2], [ТЕМА 3], [ТЕМА 4],
    [ТЕМА 5]. Шаблон [ID], у каждой 1 H1 и 2 H2. Каждый ресурс — с новым idempotency_key.
    Покажи таблицу: тема, id ресурса, QA-статус.
    ```

### 7.3. SEO и структура

16. ```text
    Подбери 5 вариантов SEO-заголовка (до 60 символов) и 3 meta description (120–160 символов)
    для статьи «[ТЕМА]».
    ```

17. ```text
    Проанализируй статью ресурса [ID]: заголовки, длину абзацев, наличие H1/H2,

18. ```text
    Добавь в статью ресурса [ID] JSON-LD разметку типа [Article/FAQPage/Product]
    и проверь её через content_validate.
    ```

19. ```text
    Перепиши заголовки H2 статьи [ID] так, чтобы они отвечали на вопросы читателя,

    ```

20. ```text
    Сделай для статьи [ID] 3 варианта первого абзаца: экспертный, дружелюбный и короткий.
    Предложи, какой лучше, и почему.
    ```

21. ```text
    Проверь статью [ID] на «воду» и канцелярит, предложи конкретную правку и примени её

    ```

## 8. Шпаргалка: задача → что вызовет агент

| Ваша задача | Инструмент Bridge |
|---|---|
| «Посмотри структуру сайта» | `site_schema`, `site_fingerprint` |
| «Какие правила у шаблона?» | `content_contract` |
| «Проверь текст» | `content_validate` |
| «Покажи статью 42» | `resource_read` |
| «Найди статьи про X» | `resource_list` (`q`, `template`, `tv_name`/`tv_value`) |
| «Как будет выглядеть?» | `resource_preview` |
| «Создай черновик» | `resource_create` |
| «Измени текст» | `resource_update` |
| «Заполни TV» | `resource_create` / `resource_update` (`tvs`) |
| «Опубликуй» | `resource_publish` (нужен approval) |
| «Удали» | `resource_delete` (запрещено по умолчанию) |

## 9. Частые ошибки и что они значат

| Ответ | Что это значит | Что делать |
|---|---|---|
| `content_qa_failed` | Текст не прошёл проверку | Исправьте по списку `errors` и повторите |
| `approval_required` | Публикация без подтверждения | Подтвердите изменение (администратор) либо опубликуйте черновик вручную в MODX |
| `approval_invalid` | Подтверждение не подходит к этому изменению/ресурсу | Запросите новое подтверждение именно для этого ресурса |
| `insufficient_scope` | У токена нет нужного права | Выдайте новый токен с нужным scope |
| `operation_disabled` | Операция выключена политикой (удаление) | Не включайте без необходимости; используйте MODX Manager вручную |
| `policy_denied` / `ip_not_allowed` | Сработала защита | Проверьте настройки и IP (см. первую инструкцию) |
| `idempotency_conflict` | Тот же ключ использован для другой операции | Сгенерируйте новый `idempotency_key` |
| `resource_not_found` | Ресурса нет или он удалён | Проверьте id |
| `invalid_filter` | Некорректный фильтр в списке | Проверьте значение (`limit` 1–100, `depth` 1–50 и т.п.) |
| `too_many_descendants` | Поддерево для `depth` слишком большое | Уменьшите `depth` или запросите уровень отдельно |

## 10. Правила безопасности для пользователя

1. **Токен — как пароль.** Не вставляйте его в чат с AI, в письма и документы.
2. **Не выдавайте scope `resource:delete` и `settings:write`** без острой необходимости.
3. **Оставьте подтверждение публикации включённым.**
4. **Проверяйте предупреждения QA**, даже если операция прошла.
5. **Правьте по одному изменению за раз** — так проще контролировать результат.
6. **Храните бэкапы** перед массовыми операциями.
7. **Если агент предлагает «обойти» защиту** — это повод проверить промпт и настройки, а не
   отключать защиту.
